# Verification Codes extension

## 1. Introduction {#intro}

A Company can request a verification code in an API, MCP, conversation, or browser response.
The Personal Agent collects it through trusted UI and submits it outside its model context.
APIs, MCP, and conversations use their existing request paths. Websites use an advertised endpoint
so the code never passes through the browser.

This page defines version 1 of the `verification-codes` extension. It uses the terms in the
[specification](/docs/spec).

## 2. Advertising support {#support}

A Company lists the extension in `extensions` in its `poppy.json` ([spec
3.3](/docs/spec#extensions)):

```json label="Excerpt from poppy.json"
{
  "extensions": {
    "verification-codes": [{ "version": "1", "endpoint": "https://example.com/poppy/verification-codes" }]
  }
}
```

A Company using the website binding lists `endpoint` and `web.browser_session_endpoint` ([spec
6](/docs/spec#web-browsing)). Other bindings need neither and omit `endpoint`.

A Personal Agent declares it on requests whose binding it implements:

```http label="Request header: Personal Agent → Company"
Poppy-Extensions: "verification-codes";v="1"
```

The Company returns verification requests only when this version was declared.

## 3. Verification objects {#requesting}

The Company creates a verification request after starting a verification for this User:

```json label="Verification request: Company → Personal Agent"
{
  "request_id": "vfy_3Hq8",
  "channel": "email",
  "sent_to": "j***@example.com",
  "length": 6,
  "expires_at": "2026-11-24T23:15:00Z"
}
```

| Field                | Req. | Description                                              |
| -------------------- | ---- | -------------------------------------------------------- |
| `request_id`         | Yes  | An opaque ID for this verification.                       |
| `channel`            | Yes  | Code source, such as email or an authenticator.            |
| `sent_to`            | No   | A masked destination hint.                                |
| `length`             | Yes  | The number of characters, counted as Unicode code points. |
| `expires_at`         | Yes  | When the request expires, as an RFC 3339 timestamp.        |
| `attempts_remaining` | No   | A positive integer: how many submissions remain.          |

The Personal Agent submits the request ID and code:

```json label="Code submission: Personal Agent → Company"
{ "request_id": "vfy_3Hq8", "code": "0A2bC5" }
```

The code is a non-empty string. The Personal Agent MUST preserve casing and leading zeroes,
without normalization. The Company validates its format.

## 4. Transport bindings {#delivery}

### APIs {#delivery-apis}

The API returns HTTP 403 with `error: "verification_required"` and the verification request in
`verification`:

```http label="Response: Company → Personal Agent"
HTTP/1.1 403 Forbidden
Content-Type: application/json
Cache-Control: no-store

{
  "error": "verification_required",
  "verification": {
    "request_id": "vfy_3Hq8",
    "channel": "email",
    "sent_to": "j***@example.com",
    "length": 6,
    "expires_at": "2026-11-24T23:15:00Z"
  }
}
```

The Personal Agent repeats the same method, target URI, and body, adding the submission in
`Poppy-Verification-Submission`:

```http label="Request: Personal Agent → Company"
POST https://api.example.com/orders/ord_7Hk2/exchanges
Poppy-Session: eyJ0eXAiOiJwb3BweS1zZXNzaW9uK2p3dCIs…
Poppy-Version: 1.1
Poppy-Extensions: "verification-codes";v="1"
Content-Type: application/json
Idempotency-Key: 9a3d7b2e-5c1f-4e8a-b6d0-2f7c4a1e9b3d
Cache-Control: no-store
Poppy-Verification-Submission: request_id="vfy_3Hq8", code="0A2bC5"

{ "item_id": "itm_4Qa", "replacement_sku": "stormline-insulated-m" }
```

### MCP {#delivery-mcp}

The tool returns `isError: true` with `verification` in `structuredContent`:

```json label="Tool result: Company → Personal Agent"
{
  "isError": true,
  "content": [{ "type": "text", "text": "Verification is required before continuing." }],
  "structuredContent": {
    "verification": {
      "request_id": "vfy_3Hq8",
      "channel": "email",
      "sent_to": "j***@example.com",
      "length": 6,
      "expires_at": "2026-11-24T23:15:00Z"
    }
  }
}
```

The Personal Agent repeats the same tool call and arguments, putting the submission in
`params._meta["personalagentprotocol.org/verification"]`, not in tool arguments:

```json label="Tool call: Personal Agent → Company"
{
  "jsonrpc": "2.0",
  "id": 8,
  "method": "tools/call",
  "params": {
    "name": "exchange_item",
    "arguments": {
      "order_id": "ord_7Hk2",
      "item_id": "itm_4Qa",
      "replacement_sku": "stormline-insulated-m"
    },
    "_meta": {
      "personalagentprotocol.org/verification": {
        "request_id": "vfy_3Hq8",
        "code": "0A2bC5"
      }
    }
  }
}
```

### Conversations {#delivery-conversations}

A Company message carries the request in `extensions["verification-codes"].verification`,
alongside its normal text:

```json label="Message: Company → Personal Agent"
{
  "id": "msg_p7Rt",
  "role": "company",
  "author": { "type": "agent" },
  "text": "I sent a verification code to your email address.",
  "extensions": {
    "verification-codes": {
      "verification": {
        "request_id": "vfy_3Hq8",
        "channel": "email",
        "sent_to": "j***@example.com",
        "length": 6,
        "expires_at": "2026-11-24T23:15:00Z"
      }
    }
  }
}
```

The Personal Agent submits the code through the same conversation's existing messages endpoint,
in `extensions["verification-codes"].submission`:

```json label="POST body: Personal Agent → Company"
{
  "id": "msg_Hc72PwZn4eKs1QxB",
  "message": {
    "author": { "type": "agent" },
    "text": "The user submitted a verification code.",
    "extensions": {
      "verification-codes": {
        "submission": { "request_id": "vfy_3Hq8", "code": "0A2bC5" }
      }
    }
  }
}
```

The Company reports the verification outcome in its normal reply.

### Websites {#delivery-websites}

A website uses this binding for a browser joined to a Session ([spec 6](/docs/spec#web-browsing)),
using the extensions declared when it joined. It performs no action and returns HTTP 403 with
the Session's `sid` and an opaque reference in a response header:

```http label="Response: Company → Personal Agent's browser"
HTTP/1.1 403 Forbidden
Cache-Control: no-store
Poppy-Verification: sid="ses_Hq3vT8nW2kLm9xRb", ref="vfy_3Hq8"
```

The Personal Agent accepts a reference only from a response its own browser received, with a `sid`
it joined that browser to. It sends the reference only to that Session's Company's `endpoint`,
with that Session's header and its access token if signed in:

```http label="Lookup: Personal Agent → Company"
POST https://example.com/poppy/verification-codes
Poppy-Session: eyJ0eXAiOiJwb3BweS1zZXNzaW9uK2p3dCIs…
Poppy-Version: 1.1
Poppy-Extensions: "verification-codes";v="1"
Content-Type: application/json
Cache-Control: no-store

{ "ref": "vfy_3Hq8" }
```

The endpoint checks the Session and token as an API does ([spec 7](/docs/spec#apis)), and binds
the reference to that Session, account context, and blocked action. It returns the same HTTP 403
JSON response as the API binding. Unknown or wrong-owner references return HTTP 400 `invalid_request`.

The Personal Agent sends the same request again with the submission header, as at an API:

```http label="Submission: Personal Agent → Company"
POST https://example.com/poppy/verification-codes
Poppy-Session: eyJ0eXAiOiJwb3BweS1zZXNzaW9uK2p3dCIs…
Poppy-Version: 1.1
Poppy-Extensions: "verification-codes";v="1"
Content-Type: application/json
Cache-Control: no-store
Poppy-Verification-Submission: request_id="vfy_3Hq8", code="0A2bC5"

{ "ref": "vfy_3Hq8" }
```

On success, the Company records verification for that Session and blocked action and returns
HTTP 204; it performs no action at this endpoint. Repeating either endpoint request after success
returns HTTP 204 without checking the code again. The browser then resumes through the website,
such as with a Continue button, without receiving the code. The website checks the recorded
verification before performing the blocked action. Actions that cannot safely resume use the
website's own verification flow instead.

The headers above are Dictionary Structured Fields ([RFC 9651](https://www.rfc-editor.org/rfc/rfc9651)).
`sid` and `ref` are Strings; `ref` has 1–2048 characters from A–Z, a–z, 0–9, `-`, `_`, and `.`.
Submission values are Strings, or Display Strings when needed. Unknown members are ignored.

### Retries and failures {#delivery-failures}

A wrong code returns the verification request through the same binding, with the same `request_id`
while it remains valid and optional `attempts_remaining`. Retrying without a submission reuses the
pending request; it MUST NOT resend a code. Resending a delivered code requires an explicit User
request through the Company's existing flow, issues a new `request_id`, and invalidates the old one.

An expired or exhausted request returns a terminal failure, not another verification request.
APIs and the website endpoint return HTTP 403 with:

```json label="Terminal failure: Company → Personal Agent"
{ "error": "verification_failed", "request_id": "vfy_3Hq8" }
```

MCP returns `isError: true` with those members in `structuredContent`. Conversations put
`{ "request_id": "vfy_3Hq8" }` in `extensions["verification-codes"].failed`, alongside normal text.
The Personal Agent stops collecting codes for that request. Unknown or wrong-owner submissions
return `invalid_request` instead.

## 5. Handling codes {#security}

The Personal Agent handles collection and submission in deterministic code. Its trusted UI
identifies the Company and shows the destination hint, if provided. It MUST get the User's
consent to send the code to that Company.

The Company MUST bind each request ID to the verified Personal Agent, User, account or signed-out
context, underlying verification, and originating request or conversation. It checks those bindings,
expiry, code length and format, and attempt limits before accepting a submission. Unknown, expired,
completed, or wrong-owner IDs MUST NOT invoke the verifier.

After verification succeeds, the original request continues under its normal authorization and
approval rules. If approval is also required, a retry carries both the approval and submission
(for APIs, `Poppy-Approval` and `Poppy-Verification-Submission`); `verification_required` does not
replace the operation. The Personal Agent MUST NOT automatically retry a code-bearing request
unless the interface's existing idempotency covers both verification and the original action.

Codes MUST NOT enter the Personal Agent's model context, message `text`, URLs, browser requests or content,
or MCP tool arguments. Both sides MUST redact codes from logs, tracing, and analytics, including
capture of submission bodies, headers, and metadata. The Company MUST omit the submission object
from recorded conversation messages, events, streams, and transcript exports, retaining non-secret
`text`. It MUST NOT echo the code in replies.

Code-bearing HTTP exchanges MUST use `Cache-Control: no-store`. The Personal Agent MUST NOT forward
the submission header across redirects.

## 6. Content schema {#schema}

The definitions describe the standalone objects. The root describes `extensions["verification-codes"]`:
`verification` or `failed` for Company messages, or `submission` for Personal Agent messages.

```json label="JSON Schema: verification-codes objects"
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "verification": { "$ref": "#/$defs/verification" },
    "submission": { "$ref": "#/$defs/submission" },
    "failed": { "$ref": "#/$defs/failed" }
  },
  "oneOf": [
    { "required": ["verification"] },
    { "required": ["submission"] },
    { "required": ["failed"] }
  ],
  "$defs": {
    "verification": {
      "type": "object",
      "required": ["request_id", "channel", "length", "expires_at"],
      "properties": {
        "request_id": { "type": "string", "minLength": 1 },
        "channel": { "type": "string", "minLength": 1 },
        "sent_to": { "type": "string", "minLength": 1 },
        "length": { "type": "integer", "minimum": 1 },
        "expires_at": { "type": "string", "format": "date-time" },
        "attempts_remaining": { "type": "integer", "minimum": 1 }
      }
    },
    "submission": {
      "type": "object",
      "required": ["request_id", "code"],
      "properties": {
        "request_id": { "type": "string", "minLength": 1 },
        "code": { "type": "string", "minLength": 1 }
      }
    },
    "failed": {
      "type": "object",
      "required": ["request_id"],
      "properties": {
        "request_id": { "type": "string", "minLength": 1 }
      }
    }
  }
}
```
